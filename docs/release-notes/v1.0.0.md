**ocr 1.0.0: the Linux release.** Start with [docs/TESTERS.md](https://github.com/pkeenan87/ocr/blob/v1.0.0/docs/TESTERS.md).

**Download:** `ocr-1.0.0-linux-x86_64.tar.gz` holds the `ocr` binary for x86-64 Linux (glibc 2.35 or later: Ubuntu 22.04, Debian 12, Fedora 36 and newer), the Claude skill (`skills/ocr`), the README, the tester guide, the license and THIRD_PARTY_NOTICES.md. Check it with the `.sha256` file beside it. On the Mac, build 1.0.0 from source; the macOS pilot binary stays at 0.2.0.

**Getting started on Linux:**

    sha256sum -c ocr-1.0.0-linux-x86_64.tar.gz.sha256
    tar xzf ocr-1.0.0-linux-x86_64.tar.gz
    sudo cp ocr-1.0.0-linux-x86_64/ocr /usr/local/bin/
    ocr server setup --model dots-ocr
    ocr server start --model dots-ocr
    ocr scan --model dots-ocr --input-file filing.pdf

Setup picks the CUDA, Vulkan or CPU build of llama.cpp for your hardware and downloads it with pdfium and the model weights; every file is checked against a pinned sha256.

CER is no more than 1 point worse than on the Mac for every engine and family except Paddle tables (the Mac crops tables with Apple Vision).

- **Use `dots-ocr` on Linux.** It is the most accurate engine for transcripts and tables. `paddleocr-vl` (the default) is the fastest and lightest, but without Apple Vision's table crops it is much weaker on tables, and it is the weakest on transcripts.
- Bates numbers: 11/11 on pleadings for all three engines, and 4/4 for each on a test document with the stamp centred under the footer.

**Changes since 0.2.0:**
- Linux release build and packaging (`.github/workflows/release.yml`), with third-party notices.
- Bates numbers off the Mac:
  - an invoice or other number inside a body sentence is no longer taken as the Bates number when the model drops the footer; this also stopped the corner request that would have read the real stamp (pleading Bates 9/11 → 11/11 for olmOCR, 10/11 → 11/11 for dots; production 90% → 100% for dots);
  - a Bates number centred under the footer is now read (a third, bottom-centre request);
  - on a sideways page olmOCR now reads the Bates corners from the turned page.
- Loop retry:
  - off the Mac, the repetition penalty is now sent as llama-server's `repeat_penalty`; the old field name was silently ignored, so a looping page was retried unchanged;
  - a loop that runs into the token limit now gets the penalty retry instead of more tokens, and such cut-off loops are recognised even when the repeated line has few letters (`By _____`) or counts up (`[801] …`, `[802] …`). On 230 pages of real court filings, Paddle on Linux lost 3 pages to this; 2 now succeed.
- The `indra-ocr` engine (CPU-only ONNX pipeline; see the README for its model license).
- The off-Mac model pipeline (resume, `--jobs`, Bates corner requests, the server lock) is now covered by integration tests on Linux and Windows CI.

**Upgrading:** the `ocr` version is part of each output's `scan_record`, so in directory mode outputs made by 0.2.0 are rescanned once.

**Known limits on Linux:**
- No Apple Vision: transcripts are not detected and their line numbers are not re-anchored; check page:line citations against the PDF.
- `--verify-json` has no second image reading, so values on scanned pages are `check`, never `verified`; only the PDF's own text verifies a value.
- A number that ends a body sentence (`…Invoice No. INV-24337.`) on a page whose footer the model dropped can still be taken as its Bates number.
- On a page stored sideways, `dots-ocr` finds no Bates number (`olmocr` does, from its rotation correction).
- Filled form fields, annotation stamps and handwriting are flagged, not read. pdfium cannot read form values and counts every form widget.
- Windows builds and passes CI but has not been run on a Windows machine, so it is not supported yet.

**Please report** any value marked `verified` that is wrong. That is the failure that matters most.
